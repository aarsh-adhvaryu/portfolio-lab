## What is built
- `service/tg_api.py`: `TgApi(token, chat_id, transport, downloader)`: `send_message` (split at 4096, buttons on the last part, returns the message ids), `edit_message` ("not modified" counts as done), `edit_markup`, `delete_message`, `answer_callback`, `chat_action`, `get_file` (`TgFileTooBig` when the Bot API refuses), `download` (stream to a file, capped at 20 MB). One wait-and-retry on HTTP 429. Every error is scrubbed of the token; a network error is a `TgError` (the poll loop backs off and retries). Real transports call `guard.require("telegram")` (the workshop never reaches the network). `roundtrip(api)` and `python -m pflab.service.tg_api` (with `PFLAB_LIVE=1`): the one real-path check, ONE message then edited in place.
- `service/tg_entrance.py`: `Entrance` (one per runtime, cached on `rt._tg_entrance`). Plain text / caption -> `intake.submit(rt, "telegram", text, attachments=[{"path","name","mime"}], model=, thinking=, reply=)`. A document or the largest size of a photo is fetched with `getFile`; a file over 20 MB gets one line ("send it from the laptop") and is NOT downloaded (nor is `getFile` called when the size is already known); a voice note / audio / video note gets one line ("type, or send a file"). Commands `/new` (`store.new_chat(con, now, channel="telegram")`), `/model` (inline picker: Auto + `gateway.models_of(gateway.current_engine())`, and the thinking levels), `/model opus|haiku|sonnet|auto` (also by model id), `/think low|medium|high|max|auto`, `/status` (picks, the queue, the engine, the month's spend), `/help`. Kept legacy commands (go to `phone.reply_for` -> `bot.handle`): `/questions /answer /decide /remember /feedback /memory /tradecheck /spend`. Buttons: `card:<msg_id>:yes|no` -> `cards.answer_card(con, msg_id, answer, "telegram")`; `undo:<rule_id>` -> `rules.undo(con, now, ref)`; `mdl:<key>` / `thk:<level>` (the picker, edited in place); the old question buttons `q:<id>:<i>` still reach `voice.handle_callback`.
- The intake's `reply(text, msg_id, final)` (worker threads, never touches the store, never raises): progress is ONE message edited in place (at most one edit per 1.5 s; identical text skipped), the FINAL answer is a NEW message (so the phone notifies) and then the progress line is deleted (edited to "Done." if the delete fails); an extra `actions=[{"id","label"}]` argument puts buttons on the final answer; a failed send is retried once.
- Hooks (small): `service/bot.py` `process(..., entrance=None)` and `_callback(..., entrance=None)`; `hq/phone.py` `poll_once(rt, timeout, transport, entrance=None)` builds the entrance with `tg_entrance.for_runtime(rt, transport)`. **Without the intake module (`pflab.entrance.intake.submit`) `for_runtime` returns None and the old reply path serves exactly as before**, so the branch works before and after `chat` merges, with no switch to flip.

## Decisions (2026-11-13)
- The entrance switches on by the intake's presence, not by a config key (old path stays as the fallback until `chat` merges).
- The model / thinking pick is kept in ONE row (`tg_prefs_s85`, scope `telegram`) and holds for later messages across `/new` until `auto` (the brief said "kept in the chat's row": the chat store's own row does not exist yet; if `chat` adds `chat_prefs`, `Entrance.prefs/set_prefs` are the only two places to switch).
- The final answer is a new message, progress is edited then deleted (an edit does not notify the phone).
- Replies from the intake are NOT written to the outbox (the chat store holds them; fewer store writers on worker threads). Sync command answers are still written to the outbox as kind `reply`, as before.
- The downloaded file is scratch under `<pm_dir>/telegram_inbox/<update_id>/`, deleted when the intake's FINAL reply arrives (also for a refused statement) or if `submit` fails; stragglers older than a day are swept on the next file. The intake keeps what it keeps.
- Retired (E6) in `bot.handle`: `/networth /guards /fds /plan /risk /tax /taxplan` (read `centre`), `/deep`, `/event`, `/quant`, `/theses`, `/research`; in `phone.reply_for`: `/calc /sim /web /research /analyse /quant /graph /clean /remind /brain /portfolio /read /watch /order /agents /board` (the HQ agents). They answer "I don't know that command". `/spend` stays. Plain words still go to the HQ board ONLY when the intake is absent; whoever retires the board (chat's leftovers of v1 layers) can then delete `phone.reply_for`'s plain-words branch and `HQ` imports.
- `pflab bot run` (the CLI poller) stays on the old path: the app's phone thread is the real bot (A42).
- Album photos (several files in one message group) arrive as separate updates and are submitted one by one.

## For the other agents
- `chat` (`post_system`, Telegram channel): to send an actions message with buttons use `telegram.enqueue_with_buttons(con, text, kind, tg_entrance.actions_to_buttons(actions), dedup_key=..., now=...)`; the action `id`s must be `card:<chat message id>:yes|no` or `undo:<rule id>`: those are what `Entrance.callback` answers. For an intake answer with buttons call `reply(text, msg_id, True, actions=[...])`.
- `chat`: `intake.submit` is called with `rt` (the Runtime) as first argument when the entrance has one (the app), else the cursor; `chat_id=None` (latest chat); `reply` may be called from any thread with `(text, msg_id=None, final=True)`; non-final calls with the same `msg_id` become edits of one message.
- `gateway`: the picker reads `models_of(current_engine())` -> `[{"key","model"}]` (`current_engine()` may return a name or a dict with `name`); the key is what is passed as `model=`. Falls back to haiku / sonnet / opus keys when absent.
- `cards`: `answer_card(con, msg_id, "yes"|"no", "telegram")`; a returned dict with `text` is shown to him as the confirmation, otherwise "Noted: Yes."
